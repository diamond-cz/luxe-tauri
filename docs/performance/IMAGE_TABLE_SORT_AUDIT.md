# 图片列表排序内存与性能检查

检查日期：2026-11-23。基线为提交 `e7136c6` 的 `src/views/mtk/isp6s/TablePane/TablePane.tsx`，优化版为本次工作区实现。

## 结论与适用边界

在本次真实 ImageTab 组件的隔离压力测试中，未发现可复现的排序持续内存泄漏。排序时的DOM、监听器计数稳定；反复挂载/卸载后回到固定基线，排序数值数组在卸载后释放。原实现存在大量重复读取、比较器内重复数值解析和过期全目录请求，容易造成临时内存峰值与卡顿，但不能将暂时上涨的工作集直接判为泄漏。

测试使用Edge headless、Vite开发模式、Fluent主题、实际ImageTab/虚拟列表和实际 `loadImageTomlFieldsBatchShared` 请求去重代码；仅替换底层Tauri IPC，生成确定性的字段数据。数据集为1,000/10,000/50,000行；Node算法基准另覆盖100,000行。数值含缺失值及 `123 [2, 3]` 一类复合文本。所有耗时是本机该夹具结果，不是实际TOML磁盘读取或Windows桌面安装包的保证值。

只读进程检查发现当前LUXE为0.2.19调试实例，其WebView2未启用远程调试端口。本轮未重启或操作用户当前实例，也未对Tauri宿主、WebView2 browser/renderer/GPU做实际排序工作集采样；这些进程的泄漏结论仍需同构建、同真实目录单独验收。未本地编译Rust/Tauri。

## 已验证的根因与优化

| 原实现 | 本次实现与行为边界 |
| --- | --- |
| 排序读取effect依赖整个sortState，升/降序都会读取全目录 | effect只依赖数据集、元数据代次与排序key；升降序复用当前列数值，不再次IPC |
| 比较器两侧每次都解析字符串；每行可能解析几十次 | 字段读取后每行只解析一次，保存为 `Float64Array`，比较器直接比较数值 |
| `entries.map(...).filter(...).slice().sort(...)` 多复制一份引用数组 | 原过滤结果本来就是新数组，直接原地排序该局部数组，原entries不变 |
| 一次全目录IPC持有全部路径与返回字段Map | 排序按最多1024行顺序分块，处理完转为标量，不把整目录字段Map留在排序状态 |
| requestId仅隔离结果，旧全目录读取仍执行到底；多个切列任务可以积压 | 每张表只执行一个排序分块，并保留一个最新待处理列；切列/关闭/卸载后不再提交剩余分块，已开始的单次invoke允许结束 |
| 当前排序列数据没有显式来源身份 | snapshot包含entries引用、revision和key，身份不符不参与排序，元数据刷新重新读 |

入口为 `TablePane/imageTableSort.ts` 的 `createImageTableSortLoader`、`sortImageRows`，由 `ImageTab` 调用。排序只保留当前列的数值数组，空间为8N字节；1万行80,000字节，10万行800,000字节，不新增全局完成结果缓存。请求去重仍调用 `src/ipc/imageScan.ts` 的原入口，其进行中Map在resolve/reject后清除。

原数值解析行为、缺失值末尾排序、相同值按原始索引稳定排序、复合字符串和自定义列公式保持原语义。取消排序恢复原目录顺序；筛选后仍使用原索引访问标量。

## 内存检查

对1万行执行100次同列正逆序切换（5组，每组20次），每组完成且请求空闲后由CDP显式GC，再读取堆/DOM/监听器；另切列24次、挂载/排序/卸载5轮。

| 观察项 | 基线 | 优化后 |
| --- | --- | --- |
| 100次排序期间DOM节点 | 1,267，五组相同 | 1,267，五组相同 |
| 100次排序期间JS监听器 | 223，五组相同 | 223，五组相同 |
| 每次卸载后DOM节点/监听器 | 23 / 160，五轮相同 | 23 / 160，五轮相同 |
| 第1至第5组GC后JS堆 | 47,771,648 → 47,985,080字节 | 46,770,012 → 46,936,624字节 |
| 快速切列后的GC堆 | 48,782,860字节 | 46,715,564字节 |
| 卸载后GC堆 | 43,757,060字节 | 43,671,472字节 |
| 五轮卸载后GC堆范围 | 43,785,080–43,944,480字节 | 43,702,684–43,848,148字节 |
| 切列后到卸载的backing storage变化 | 不含排序TypedArray | 26,602,266 → 26,522,252字节，释放约80KB |

少量堆预热、JIT/框架缓存变化不能证明泄漏；这里的关键证据是DOM和监听器没有逐轮累积，卸载后数据空间被回收。本测试时长和规模不能证明所有运行时长、所有进程绝对无泄漏。

第一轮使用Playwright控件Locator发出操作时出现脱离DOM与监听器逐轮增长；随后用相同组件、相同排序路径、直接DOM事件复测，稳定回到上述基线。定位操作产生的测试工具引用会干扰保留计数，因此最终内存结果使用无控件句柄保留的直接DOM操作；未为这个测量干扰修改产品逻辑。

## 性能与请求量

1万行真实组件中，先完成当前列加载，再测100次正逆序：

| 指标 | 基线 | 优化后 |
| --- | --- | --- |
| 响应中位耗时 | 98.50 ms | 20.18 ms |
| P95 | 110.27 ms | 30.06 ms |
| 排序字段请求次数 | 100 | 0 |
| 排序字段累计读取行数 | 1,000,000 | 0 |

这100次期间仍可能有虚拟列表的可见行补读；统计专门区分了排序字段读取，不把可见行读取声称为零。

快速切换两列24次：基线发出12个全量请求（其中相同进行中请求被原共享入口合并），读取120,000行，单请求10,000行；优化后发出17个小分块，累计17,168行，单请求最多1024行，同表排序最多一个请求在途。命令次数略多，但实际读取行数减少约85.7%，停止了被替代任务的后续批次。

Node 22.23.5独立执行实际原解析器/比较器与新排序模块，每种规模12轮，包含创建排序行和一次新数值解析的中位值：

| 行数 | 基线 | 优化后 | 基线解析调用/次 | 新版解析调用/列加载 |
| --- | --- | --- | --- | --- |
| 10,000 | 53.13 ms | 4.19 ms | 238,550 | 10,000 |
| 50,000 | 355.44 ms | 25.04 ms | 1,422,036 | 50,000 |
| 100,000 | 810.49 ms | 53.97 ms | 3,042,464 | 100,000 |

首次排序仍需读取该列全部字段。真实组件夹具中单次首排结果为：

| 行数 | 基线全量读取 | 新版1024行分块 |
| --- | --- | --- |
| 1,000 | 27.59 ms | 26.02 ms |
| 10,000 | 71.32 ms | 72.58 ms |
| 50,000 | 261.46 ms | 355.99 ms |

夹具每次IPC模拟约1ms等待，分块在浏览器定时器和跨请求等待上有额外成本，不能宣称首次大目录排序总耗时全面下降。早期256行试验使5万行首排达到约1243ms，因此按实际结果调整为1024行。当前取舍是限制临时内存/无效请求、明显改善反复正逆序，并让可见行请求能穿插执行。真实磁盘成本、IPC固定开销、冷热缓存仍需原生环境测量。

## 回归与复测

正式行为测试：`node --test scripts/image-table-sort.test.mjs`，已接入 `npm run sync:test`。覆盖数值/缺失/稳定排序、分块数量与8N空间、快速切列只保留最新任务、最多一个活动请求、取消/卸载停止后续批次、失败后恢复。现有 `image-exif` 测试继续验证共享请求代次隔离和settlement清理。
