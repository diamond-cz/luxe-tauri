# LUXE CPU、内存回收与性能维护

本文记录当前项目已有的回收链路和前端性能约束，供新增功能时直接沿用；本文件以仓库现有代码为准。

| 层级 | 现有入口 | 职责 |
| --- | --- | --- |
| 前端触发 | `src/hooks/useIdleMemoryTrim.ts` | 可见窗口空闲 8 秒调用轻量回收；窗口隐藏或离开 MTK 页面时要求清理缓存 |
| IPC 限流 | `src/ipc/memory.ts` | `trimMemory(clearCaches)` 合并并发请求；普通回收至少间隔 30 秒，清缓存至少间隔 5 秒 |
| Rust 回收 | `src-tauri/src/memory_trim.rs` | 后台线程按 `clearCaches` 决定是否清理图片和 C++ 解析缓存，再调用 `mi_collect(true)`；Windows 上临时将 WebView2 内存目标设为 LOW，1.5 秒后恢复 NORMAL |
| 图片缓存 | `src-tauri/src/image_scan/mod.rs` | 按既有预算限制缓存；清理时淘汰缓存并隔离旧任务结果 |

## 新功能接入规则

1. 大对象要有明确的所有者和生命周期。图片、Canvas 像素、Blob URL、解析结果等，在切换文件或卸载组件时释放；异步任务用取消标志或代次忽略过期结果。
2. Rust 缓存应设置容量预算，并在 `clear_memory_caches()` 或对应缓存的 `clear()` 中纳入清理。避免缓存锁跨磁盘读取、解码或耗时计算。
3. 前端清理触发统一使用 `trimMemory()`；需要释放跨页面缓存时调用 `trimMemory(true)`。不要直接调用 WebView2 API，也不要在高频事件中反复请求回收。
4. 所有 `ResizeObserver`、滚动和指针监听都要在卸载时解绑；更新 React 状态前比较测量值。持续的观察器、状态、布局反馈会同时推高 CPU 与 renderer 内存。
5. 区分“可回收缓存”和“仍被引用的对象”。`mi_collect` 或 WebView2 LOW 只能促使已无用内存归还；不能替代取消任务、关闭资源或清除引用。

## 图片列表和详情面板的性能约定

新增图片字段、预览模式或详情卡片时，沿用以下处理方法：

| 场景与风险 | 处理方法与现有入口 |
| --- | --- |
| 大图片列表全量挂载、解码或预加载 | `TablePane.tsx` 已实现固定行高、可视窗口切片和有限 overscan；新增列也应按窗口加载必要 TOML 字段，控制预取范围与并发，不把整目录解码结果常驻内存 |
| 固定详情表反复渲染 | `Isp6sAeVisual.tsx` 的 `DetailsPanel` 使用 `memo` 和稳定 props 隔离图片列表、解析进度及分隔条更新；AE Basic 的 EXIF/Normal/Face/LCE/bcompare 与 ToneMap 的 EXIF/LCE/Tone.cpp 均只挂载当前标签内容 |
| 折叠后组件和监听器仍占资源 | 详情面板折叠时卸载子树，展开时恢复滚动位置；观察器、事件监听和定时器随卸载清理，异步 IPC 返回用取消标志忽略；滚动恢复观察器找到目标后断开，等待超时或卸载时也断开 |
| 子组件回传 binding 引发父子反馈循环 | 使用 `useCallback` 稳定父级 `onMode`，避免“父渲染 → 回调引用变化 → 子 binding effect → 父 setState → 父渲染”；effect 仍保留必要依赖，不能通过删除依赖掩盖问题；AE.CPP 与 Tone.cpp 源码绑定只传给各自的 bcompare/Tone.cpp 对比面板 |
| 每个单元格各自创建 tooltip 状态和节点 | Normal/Face 使用已有 `GlobalTitleTooltip` 的委托入口：`title`、`data-tooltip-position="below-start"`、`data-tooltip-wrap="true"`、`data-tooltip-max-width={520}`；需要局部 tooltip 时先评估实例数与清理成本 |
| 尺寸观察触发布局与状态循环 | `ResizeObserver` 仅在宽高变化时更新状态；异步 schema 加载后才出现的 viewport 要重新绑定观察器，参照 `FaceTable.tsx` 的 `[schema]` 依赖 |

虚拟化优先用于行数很多的同构列表。固定详情表包含合并单元格、折叠区块和编辑操作，优先隔离渲染与按需挂载；若实测仍有大量节点开销，再评估虚拟表，并验证合并单元格、键盘操作、滚动恢复和可访问性。

MTK 私有 EXIF 自动导入优先直接复用合法同名 TOML（含来源标记/旧无标记），不重新读 JPEG、不遍历业务指纹、不反复重写；没有 TOML 才 native 读取 APP5/6/7。右键显式重读 JPEG 后以有效新结果完整覆盖 TOML，不解析旧业务、不比较/合并字段；旧文件仅保留有界原字节快照用于并发重验，不能为省 I/O 取消安全检查。无有效新内容/失败保留旧文件。左键强制 DebugParser 有效新结果覆盖，两者不删除原图片/EXIF。普通切图、批量字段和 EXIF 详情只读准备后的 TOML，不再隐式解码 JPEG。未知/部分状态保存为真实待兜底的 TOML，解码器/头库变化不再触发对已有文件自动对账，需要右键主动重读覆盖。仍复用原字段缓存与 `trimMemory(true)` 清理链路，不将图片字节或整目录完整 EXIF 常驻内存。Rust 全字段缓存最多 96 项且估算有效载荷不超过 16 MiB，按键缓存最多 512 项且不超过 8 MiB；JPEG 元数据和文本单次读取上限均为 16 MiB。数据源路径、类型和文件签名共同隔离缓存；当前图片已有全字段缓存时，批量接口直接抽取需要的键。前端批量字段的进行中请求另按 `{ entries, revision }` 隔离并在结束后释放，不缓存完成结果；列表、排序、Apply 和 AE/ToneMap 热力图均传递内容代次，旧任务不得回填新缓存或清掉新代次 loading 标记。详见 [MTK JPEG 私有 EXIF](../features/MTK_NATIVE_EXIF.md)。

EXIF 的结构化详情通过 `load_image_exif` 按当前图片从已准备 TOML 读取，不新增全目录或完成结果缓存；普通模块切换复用同一只读 TOML快照（detail revision/路径未变化时），切图/目录或内容代次变化时才丢弃。仍受元数据 IPC 的 2 任务队列限制。卸载后忽略迟到结果；普通字段按可视行渲染，AE_Table 每块使用单个等宽文本节点（每块最多 65,536 值、最多 64 块；形状必须完整），只挂载当前模块/统计/诊断页。统计区的非被动 wheel 监听只在 Shift 横向滚动实际生效时阻止默认行为，卸载即解绑；Detail 模块诊断上限 256 条。TOML 来源元信息及统计不进入列表字段缓存的别名空间。旧合并文件/兼容 Rust 合并 API 的混合来源诊断只保留当前模块计数（当前右键不再生成合并结果），native_merge在保存/读取投影时各做一次有界聚合，不累计历史模块行或克隆旧诊断列表；读取时取走来源对象中的modules向量复用，不重写旧文件。DP文本转换直接stamp已解析root再输出，避免展示字段字符串和额外序列化/反序列化往返。

`MetadataProgress.tsx` 仅用于导入准备及手动 EXIF/DebugParser 目录任务，位于图片列表卡片内部，不再额外挤动左右工作区的卡片顶边。`PREPARE` 安全预检/复制与 `TOML` 写入按已处理图片数（含失败）展示真实进度；`QUEUED`、外部工具 `DP` 及 `REFRESH` 使用不确定进度，不能按耗时或文件大小模拟工具百分比。任务结束即拒绝迟到 Channel 回调，不增加 timer/observer/缓存。普通点击字段/详情取消进度 Channel 和反复出现的进度条。准备任务及进度属于共享 `imageDir`，单工作区去重、最多 16 个进行中导入且结束释放，不缓存完成后的全目录结果。共享 `Rayon 1.10.0` 元数据池按核数上限 1–2 worker，每 worker 一次只持有一图文档，有界 channel 只传轻量完成消息，协调线程汇总进度，不每图无限spawn/collect。目录索引预算 262,144 项，单图文本仍限 16 MiB；两图并行是峰值对象的明确tradeoff，不宣称已经实测节省总内存。源、目标及父目录通过有界检查，写入失败保留原文件。右键删除文件的API/UI/实现已移除；左键DP权威覆盖前明确确认目录。写入后 `clear_memory_caches()` 递增缓存代次阻止旧读取重新驻留，前端 `metadataRevision` 使详情、列表、热力图和会话字段失效。导入、native 覆盖与 DP 解析任务互斥，结束即释放任务标记；切目录/切页不能让旧刷新或迟到进度覆盖新数据集。

native reader 64 KiB BufReader 在 SOS/EOI 停止，seek跳过非APP5/6/7标准EXIF/缩略图/像素表；私有扫描引入 `memchr 2.8.0` 默认std运行时SIMD分派，不强制AVX2。单图枚举cache最多16身份/2MiB估算向量，infer/resolve复用后随调用释放；native文本只parse一次、root直接stamp、最终serialize一次，去掉原多轮TOML和指纹遍历。既有 `toml 0.8.2` 未盲目替换，真实收益由可选CI release fixture benchmark或同数据集桌面trace量化；不把代码优化当作实际耗时/内存降幅。

缓存预算以代码常量为准。当前 `TablePane.tsx` 的下拉缩略图上限为 160 项，局部字段缓存为 768 项，共享字段缓存为 4096 项；图片列表悬浮预览延迟请求源图生成 448px 图像，Rust 缓存最多保留 8 张，滚动、离开或卸载时前端清除引用并隔离过期结果；批量缩略图使用固定 2 线程 Rayon 池，避免按图片数量无限创建解码任务；`workspaceSession.ts` 最多保留 16 个工作区，每个工作区最多保留 8 个源码滚动位置。新增缓存应同时说明容量、淘汰条件和清理入口，避免只限制条目数却存入完整大对象。

`WorkspaceColumns.tsx` 管理 AE Basic 和 ToneMap 的横向折叠：拖到边缘或点击标题栏图标隐藏对应列，边缘图标恢复最后的展开比例。左列包含图片列表与详情/LCE 区，隐藏时整列收起；详情区自身的纵向比例仍独立保留。横向隐藏用 `hidden` 保留两个组件实例，以免丢失源码草稿、撤销记录、Apply 结果和热力图选择；不会复制额外的图片或解析缓存，仍沿用现有预算和离开页面时的清理入口。折叠方向记录在各自 `workspaceSession` 中，切换标签后可恢复，本次不新增 TOML 字段。布局保存仅接收两侧都展开的比例，不能用 0/100 覆盖恢复值；分割器隐藏时不更新顶部参数路径栏的对齐位置。

本次 Isp6s 优化的直接教训是：虚拟列表不能修复渲染反馈循环；应先用 DevTools 的 React/Performance 记录确认空闲时是否仍在提交、布局或绘制，再决定是否增加虚拟化。

## 验证方法

- 在相同页面和相同数据集下，记录打开页面、切换页面、隐藏窗口、空闲 30 秒后的宿主与 WebView2 各子进程工作集和 CPU 增量；重复多轮，关注基线是否持续上升。
- 用父子进程关系及命令行确认 WebView2 归属，并区分 browser、renderer、GPU 进程。`Get-Process` 的 `CPU` 是累计 CPU 秒数；采样间隔内的 CPU 秒差除以实际间隔才反映负载，不能把累计值当占用率。比较时固定是否按逻辑处理器数归一化，并记录工作集及私有字节。
- 先用 WebView2 DevTools Performance 定位空闲时仍在运行的脚本、布局或绘制，再修改对应组件。任务管理器的 LUXE 汇总值不能区分 renderer 与 Rust 宿主。
- UI 回归覆盖加载源码后空闲、切换图片和详情标签、折叠再展开、切换文件、离开页面及隐藏再恢复窗口；确认空闲提交次数收敛、滚动可恢复、提示与编辑仍可用，过期请求不覆盖新文件。性能数值必须使用相同构建模式比较；类型检查或构建通过不代表已经测得 CPU、内存降幅。
- 前端改动本地运行 `npm run typecheck`；Rust 回收或托盘退出链路只运行不编译的格式/静态检查，Rust 编译与测试由 `.github/workflows/ci.yml` 执行。多开时在 CI 产物或已有可运行版本中验证托盘重启仅替换当前实例，其他实例继续运行；切换图片目录只清理当前进程的缩略图目录。
